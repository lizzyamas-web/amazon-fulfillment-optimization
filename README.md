# Amazon Fulfillment: Optimizing Labor Cost and On-Time Order Processing

**Unit 11 — Final Project Part 1: Optimization Engine**

## Overview
Independent educational simulation of an Amazon-style regional fulfillment center. Analyzes 100 staffing/expedited-processing combinations to minimize daily variable fulfillment cost (USD) and maximize the share of orders ready before processing deadlines (%). This project does **not** use Amazon internal data or describe Amazon's actual operating performance.

## Business context
The approved Unit 9 proposal focuses on labor cost versus on-time order processing. More staffing and expedited throughput can improve service at greater expense. Amazon's published filings and fulfillment research motivate the problem; all numeric model inputs are illustrative.

## Decisions and objectives
- Workers scheduled per shift: 30, 35, ..., 75.
- Expedited share: 0%, 5%, ..., 45%.
- Minimize `daily_cost_usd`; maximize `on_time_pct`.

## Approach and data provenance
`data/fulfillment_scenarios.csv` has exactly 100 synthetic rows generated by reproducible Python equations in the notebook (seed 42 reserved; fixed hourly demand profile). See `data/SIMULATION_METHOD.md` for formulas, ranges, and caveats, and `data/data_generation_prompt.txt` for the generation specification. This is Python-generated synthetic data, **not** LLM-generated data and not public Amazon records.

The Pareto test handles mixed objective directions: A dominates B when A costs no more, has at least as high on-time performance, and is strictly better in at least one dimension. Five strategies compare frontier points after normalized scoring: balanced, equity, cost priority, on-time priority, and weighted 60/40.

## Setup and reproduction
```bash
python -m venv .venv
# Windows: .venv\Scripts\activate
# macOS/Linux: source .venv/bin/activate
pip install -r requirements.txt
jupyter notebook optimization_engine.ipynb
```
Run **Kernel > Restart & Run All**. The notebook checks the CSV against its own generation logic, validates the data, computes the full frontier, prints dominated examples, saves the five strategies, and regenerates both figures. Execute from the repository root.

## Findings
The notebook prints the precise counts and strategy values. Only nondominated configurations should be considered for tradeoff selection. Because cost and service are in different units, balanced and weighted scores normalize both objectives before comparison. A dominated option is inferior to at least one feasible-in-the-unconstrained-space alternative; it is **not** necessarily inferior to every frontier option.

## Limitations and future work
Synthetic throughput-to-service proxy, not order-level deadline modeling; simplified break coverage, workstation utilization, and expedited processing; no calibration against Amazon warehouse data. In Unit 13, add constraint filtering for budget, workstation capacity, shift/break rules, expedited-lane capacity, and at least 90% on-time service, followed by a heuristic agent with explicit infeasibility handling and scenario tests. Constraints are intentionally not used to filter the Unit 11 frontier.
